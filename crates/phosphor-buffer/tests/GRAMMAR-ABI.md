# `T083` — grammar ABI check

The written answer to the one unknown the M-0 spikes surfaced and did not close
([SPIKES.md](../../../docs/SPIKES.md), *"Grammars — the first-class twelve"*): the grammar
crates were generated by tree-sitter CLIs spanning **0.23–0.25**, our runtime is **0.26**, and
tree-sitter versions its language ABI.

Machine-checked by [`grammar_abi.rs`](grammar_abi.rs) — six tests, run with
`cargo test -p phosphor-buffer --test grammar_abi`. Fixtures live in [`fixtures/`](fixtures).
Verified **2026-08-11** on `tree-sitter 0.26.12`, macOS / darwin 25.5.0.

---

## Verdict

**The ABI question is closed: all eleven load and parse. No downgrade, no substitution, no
dropped language.** `T037` may proceed on the assumption it stated.

The runtime reports **`LANGUAGE_VERSION` = 15**, **`MIN_COMPATIBLE_LANGUAGE_VERSION` = 13**.
Every shipped grammar is generated at ABI 14 or 15 — comfortably inside that window, and never
*above* it, which is the only direction tree-sitter cannot tolerate (it is backwards- but not
forwards-compatible). **The 0.23–0.25 binding spread turned out not to matter**, because the
grammars talk to the runtime through the ABI number baked into `parser.c`, not through the
`tree-sitter` version their crate happened to be tested against.

Two grammar *coverage* defects did fall out, in JSON and Scheme. Neither is an ABI failure;
both are recorded below and asserted in code.

### What "PASS" means here

Not "`parse()` returned `Some`". tree-sitter recovers from anything, so a returned tree proves
nothing — the check walks the whole tree and fails on **any `ERROR` or `MISSING` node**. The
fixtures are deliberately dense: generics, macros and `let`-else in Rust; `satisfies`, mapped
types and `declare module` in TypeScript; private fields and labelled breaks in JavaScript;
structural-pattern `match` and the walrus in Python; anchors, merge keys and both block-scalar
styles in YAML; arrays-of-tables, all four integer radices and offset datetimes in TOML;
`@supports`, `:is()` and `underline wavy` in CSS; embedded `<script>`/`<style>` in HTML;
footnotes, setext headings and reference links in Markdown.

Ten of the eleven arrive transitively through `ratatui-code-editor`'s `grammars-phosphor`
feature and cargo unifies them, so this test exercises **the same object code `BufferView` will
link**, not a parallel copy. `cargo tree -d` shows a single `tree-sitter 0.26.12`;
`cargo deny check bans` is clean.

## The Steel answer

> **Yes — `tree-sitter-scheme 0.24.7` parses real Steel. Use it, with two documented gaps that
> cannot occur in `runtime/*.scm`.**

`runtime/` has only a placeholder, so the fixture is written as what `init.scm`, `keymaps.scm`
and `leader.scm` will be once `T033` writes them, and it is deliberately not `(+ 1 2)`. It
parses with zero `ERROR` nodes while exercising:

- `define`, `lambda` (including an improper `(x . rest)` list), `let` with square-bracket
  bindings, `cond`/`when`/`unless`, named `let` recursion
- `require`, `require-builtin`, `provide`
- **quasiquote-built leader trees** — `` ` ``, `,` and `,@` splicing a list produced at load time,
  which is how the which-key tree gets its picker entries
- **`#\char` key literals** — `#\space`, `#\escape`, `#\tab`, `#\newline`, `#\a`, `#\x41`
- **strings with real escapes** — `\"` (needed for the `"a` named-register binding), `\\`, `\t`,
  `\n`, `\x41;`
- **keyword arguments** — `#:count`, `#:register`, `#:transparent`, including `[name default]`
  optionals. `#:kw` is a first-class `keyword` node in this grammar (`grammar.js:240`), which is
  the single most load-bearing Steel-ism and the thing most likely to have failed
- `struct`, `define-syntax` + `syntax-rules`, `define/contract`, `#true`/`#false` long booleans
- quoted vectors `'#(…)`, the numeric tower (`1/2`, `#xff`, `#b1010`, `#o17`, `1e3`), threading
  symbols `~>`, and all three comment forms (`;`, `#| |#`, `#;`)

`steel_reader_boundary_is_characterised` asserts each of those individually, so a regression
names the construct rather than just the file.

### Gap 1 · R7RS bytevectors `#u8(…)`

`grammar.js:306` defines `byte_vector` as `seq("#vu8(", …)` — the R6RS spelling only. `#u8(0
255)` produces an `ERROR`.

**Impact: none.** Steel writes bytes with `(bytes …)`, and no bytevector literal belongs in a
keymap or a hook. Recorded so it is a known quantity, not a surprise at S4.

### Gap 2 · `#%`-prefixed identifiers

`grammar.js:19` excludes `#` from `symbol_element`, so `#%plain-lambda` and friends do not lex
as symbols. These are Steel compiler internals; they must never appear in `runtime/*.scm`. If
one ever does, highlighting degrades for that form and nothing else — the parse still returns a
usable tree.

Both gaps are asserted **in the failing direction** by
`steel_reader_boundary_is_characterised`. If upstream fixes either, that test goes red and we
delete the entry rather than carrying a stale workaround.

## The JSON finding

`tree-sitter-json 0.24.8` **rejects a `+` exponent sign.** `[1e+2]`, `[1E+2]` and `[1e+21]` all
produce `ERROR` nodes; `1e2`, `1E2`, `1e-2` and `1E-2` are fine.

RFC 8259 §6 is explicit — `exp = ("e" / "E") [ minus / plus ] 1*DIGIT` — so this is a spec
violation, not a strictness choice. The grammar has:

```js
const signedInteger = seq(optional('-'), decimalDigits);
const exponentPart  = seq(choice('e', 'E'), signedInteger);   // no '+'
```

**It is hit in practice.** `JSON.stringify` emits `1e+21` for magnitudes at or above 1e21, so
any JSON written by JavaScript containing a large number lands an `ERROR` node on that token.

Status: `0.24.8` (2024-11-11) is the newest published version, and **`master` in
`tree-sitter/tree-sitter-json` still has the same rule** — this is not fixed by upgrading.

**Not an ABI failure**, and not a reason to drop JSON: the grammar loads at ABI 14, and
tree-sitter recovers, so the blast radius is one mis-highlighted number token per occurrence.
`json_exponent_plus_sign_is_still_broken` asserts the bug is still present, so the day upstream
fixes it the test goes red and the `+` forms go back into the fixture.

**This one needs a decision and is escalated rather than taken here** (it would be a third
vendored fork, which plan §2 does not contemplate). Cheapest options, in order:

1. **Accept and document.** Zero cost, zero risk; one mis-highlighted token in rare JSON.
2. **Upstream a one-token PR** — `optional(choice('-', '+'))` in `signedInteger` — and accept
   option 1 until it lands. No local carry.
3. **Vendor `tree-sitter-json`** as a third fork. Correct immediately, but buys a permanent
   `just vendor-diff` obligation and a regenerated `parser.c` for a one-character grammar
   change. Only worth it if a real corpus turns out to be full of `e+`.

Recommendation: **1 + 2.**
